# Переход на типы пространств BZ-167

Процедура выполняется оператором отдельно от разработки и тестов. Проверка `/v0/decisions/check` должна оставаться недоступной до завершения перехода. Новый бинарник проверяет строгую модель при старте и не поднимает endpoint на старой/переходной модели.

1. Зафиксировать store, текущую модель, снимок tuples и доверенный источник владельцев/типов. Остановить все writers отношений и изменения бизнес-данных пространств до финальной сверки. Создание типа по существующим membership запрещено: в personal могут находиться ошибочные роли.
2. Подготовить **полную** JSON-выгрузку `{space_id,owner_id,space_type}` из доверенного источника. Все ID ненулевые UUID, type — personal/shared. Утилита сопоставляет владельца с сохранённым owner. Пример:

   ```json
   [{"space_id":"db2483d1-c55d-4684-ad48-8ed4ab382015","owner_id":"5b455ab4-1f63-40f6-83c8-302db5a61c73","space_type":"personal"}]
   ```

3. Опубликовать `fga/transition-model.fga` в выбранный store штатным инструментом OpenFGA. Она допускает markers personal/shared и сохраняет прежнюю модель прав на время подготовки. Не направлять на неё новый check. Сохранить полученный model ID явно.
4. Собрать утилиту и выполнить dry run (без `-apply`):

   ```sh
   go build -o /tmp/space-types ./cmd/space-types
   /tmp/space-types -api-url "$FGA_URL" -store-id "$FGA_STORE_ID" -model-id "$FGA_TRANSITION_MODEL_ID" -input /secure/path/spaces.json
   ```

   Выход — количество пространств и точные недостающие tuples. Дубли выгрузки, неизвестные ID, пропуски, отсутствие/несовпадение/несколько owner, несовпадение или два markers блокируют **весь** план до первой записи. Учитываются и ссылки note/reminder на пространства без owner. Пустой экспорт допустим только для store без пространств и таких ссылок. Выгрузка не создаёт отсутствующие пространства и не исправляет владельцев автоматически.
5. Проверить план. При всё ещё остановленных writers запустить ту же команду с `-apply`. Записываются только недостающие `space:<id>#personal/shared@user:*`; владельцы, записи и участники не меняются. Batch содержит до 100 markers. Частичный сбой требует нового dry run до повторного apply: межпакетной транзакции нет. Повтор после успеха выдаёт пустой writes. Утилита после записи перечитывает store и проверяет полноту.
6. Опубликовать `fga/auth-model.fga`, сохранить строгий model ID. Выполнить контрольные checks owner personal delete → deny, owner personal content → allow, чужой direct owner personal content → deny, owner shared delete → allow, admin shared delete → deny. Пустой или двойной тип должен давать deny.
7. Развернуть все экземпляры writer/check с одинаковыми `openfga.store_id` и `openfga.model_id`, `apply_model_on_start: false`. `model_id` и `apply_model_on_start: true` несовместимы. Не полагаться на latest при нескольких экземплярах. Публикация следующей модели не меняет уже закреплённый ID. Запуск блокируется, если закреплённая модель семантически не совпадает со строгой моделью бинарника, либо не загружена политика Casbin.
8. Подключить обновлённого отправителя sync: для create space обязательны `resource.attributes.space_type`, `relations.owner.type=user`, owner.id доверенного пользователя. Owner и один marker записываются одной FGA Write. Тип неизменяем; personal delete/member и изменения участия owner отклоняются в старом resource-envelope с 400. Повторный create существующего пространства — 409, без обещания idempotency replay. Затем включить трафик check и возобновить writers.

Ограничения текущего sync: реализованы записи создания ресурсов и новые guards; общая реализация update/delete/member tuples и идемпотентность не входят в BZ-167. Read-before-write guards не предоставляют транзакции между БД и FGA. Конфликтующие markers приводят к deny, поэтому конкурентные изменения во время переноса запрещены организационно.

## Откат

Закрыть новый check на gateway/внутреннем маршруте, остановить несовместимых writers. Сохранить строгую модель и markers, запреты personal и защиту owner. Нельзя переключаться на старую/переходную разрешающую модель после активации. Исправить или развернуть совместимый бинарник, снова выполнить проверки и сверку model ID перед открытием трафика. Старый бинарник без privacy guards не является безопасным откатом writer. Удалять markers или восстанавливать права personal из старого снимка автоматически нельзя.

## Изолированные проверки

Интеграционные тесты создают свои временные stores; адрес принимается только на loopback. Запускать против отдельного OpenFGA с memory datastore, без production-данных:

```sh
AUTH_TEST_FGA_URL=http://127.0.0.1:8080 go test ./fga ./internal/service/fga ./internal/service/spacemigration ./internal/api/v0
```

Без переменной эти интеграционные тесты пропускаются. `make test` запускает race detector; перед приёмкой передайте ему URL отдельного тестового OpenFGA, чтобы включить реальные проверки. Docker/submodule инфраструктура проекта утилитой не изменяется.

Для проверки реальной доставки аудита дополнительно задайте `AUTH_TEST_RABBITMQ_URL` с адресом отдельного loopback RabbitMQ и выполните `go test ./internal/storage/rabbitmq`. Тест создаёт уникальную очередь, проверяет доставку и удаляет только свою очередь. Полный приёмочный запуск: обе переменные окружения + `make lint`, `make test`, `make build`.
