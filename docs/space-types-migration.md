# Переход на типы пространств BZ-167

Процедура выполняется оператором отдельно от разработки и тестов. Проверка `/api/v0/decisions/check` должна оставаться недоступной до завершения перехода. Новый бинарник проверяет строгую модель при старте и не поднимает endpoint на старой/переходной модели. `EnsureDecisionModel` ничего не мигрирует: он сверяет структуру protobuf с моделью, встроенной в эту сборку. Перестановка повторяющихся узлов тоже может считаться отличием, даже если права эквивалентны.

1. Зафиксировать store, текущую модель, снимок tuples и доверенный источник владельцев/типов. Остановить все writers отношений и изменения бизнес-данных пространств до финальной сверки. Создание типа по существующим membership запрещено: в personal могут находиться ошибочные роли.
2. Подготовить **полную** JSON-выгрузку `{space_id,owner_id,space_type}` из доверенного источника. Все ID ненулевые UUID, type — personal/shared. Утилита сопоставляет владельца с сохранённым owner. Пример:

   ```json
   [{"space_id":"db2483d1-c55d-4684-ad48-8ed4ab382015","owner_id":"5b455ab4-1f63-40f6-83c8-302db5a61c73","space_type":"personal"}]
   ```

3. Опубликовать `fga/transition-model.fga` в выбранный store штатным инструментом OpenFGA. Она допускает отметки created, personal/shared и has_personal_space и сохраняет прежнюю модель прав на время подготовки. Не направлять на неё новый check. Сохранить полученный model ID явно.
4. Собрать утилиту и выполнить dry run (без `-apply`):

   ```sh
   go build -o /tmp/space-types ./cmd/space-types
   /tmp/space-types -api-url "$FGA_URL" -store-id "$FGA_STORE_ID" -model-id "$FGA_TRANSITION_MODEL_ID" -input /secure/path/spaces.json
   ```

   Выход — количество пространств и точные недостающие tuples. Дубли выгрузки, неизвестные ID, пропуски, отсутствие/несовпадение/несколько owner, несовпадение или два markers блокируют **весь** план до первой записи. Учитываются и ссылки note/reminder на пространства без owner. Пустой экспорт допустим только для store без пространств и таких ссылок. Выгрузка не создаёт отсутствующие пространства и не исправляет владельцев автоматически.
5. Проверить план. При всё ещё остановленных writers запустить ту же команду с `-apply`. Для каждого пространства план добавляет общую отметку UUID `space:<id>#created@user:*` и отметку его типа `space:<id>#personal@user:*` или `space:<id>#shared@user:*`, если они отсутствуют. Для каждого владельца personal план также добавляет недостающую отметку `user:<owner>#has_personal_space@user:<owner>`. Для двух пространств (одного shared и одного personal) при отсутствии всех отметок ожидаются пять записей. Если записаны оба типа и отметка владельца personal, план добавит только две отметки created. Batch содержит до 100 markers. Частичный сбой требует нового dry run до повторного apply: межпакетной транзакции нет. Повтор после успеха выдаёт пустой writes. Утилита после записи перечитывает store и проверяет полноту.
6. Опубликовать `fga/auth-model.fga`, сохранить строгий model ID. Выполнить контрольные checks owner personal delete → deny, owner personal content → allow, чужой direct owner personal content → deny, personal content с дополнительным shared-parent для постороннего → deny, owner shared delete → allow, admin shared delete → deny. Пустой или двойной тип должен давать deny.
7. Развернуть все экземпляры writer/check с одинаковыми `openfga.store_id` и `openfga.model_id`, `apply_model_on_start: false`. `model_id` и `apply_model_on_start: true` несовместимы. Не полагаться на latest при нескольких экземплярах. Публикация следующей модели не меняет уже закреплённый ID. Запуск блокируется, если закреплённая модель структурно не совпадает со строгой моделью бинарника, либо не загружена политика Casbin.
8. Подключить обновлённого отправителя sync: для create space обязательны `resource.attributes.space_type`, `relations.owner.type=user`, owner.id доверенного пользователя. Сервис записывает owner, created и тип одной транзакцией OpenFGA, а для personal в ту же транзакцию включает has_personal_space. Все writers должны сохранять стандартное поведение OpenFGA при дубликате tuple — отказ всей транзакции. Тип неизменяем; personal delete/member и изменения участия owner отклоняются в старом resource-envelope с 400. Повторный create существующего пространства — 409, без обещания idempotency replay. Затем включить трафик check и возобновить writers.

Ограничения текущего sync: реализованы записи создания ресурсов и новые guards; общая реализация update/delete/member tuples и идемпотентность не входят в BZ-167. Read-before-write guards не предоставляют транзакции между БД и FGA. Конфликтующие markers приводят к deny, поэтому конкурентные изменения во время переноса запрещены организационно.

## Откат

Закрыть новый check на gateway/внутреннем маршруте, остановить несовместимых writers. Сохранить строгую модель и markers, запреты personal и защиту owner. Нельзя переключаться на старую/переходную разрешающую модель после активации. Исправить или развернуть совместимый бинарник, снова выполнить проверки и сверку model ID перед открытием трафика. Старый бинарник без privacy guards не является безопасным откатом writer. Удалять markers или восстанавливать права personal из старого снимка автоматически нельзя.

## Проверки

Unit-тесты в `make test` проверяют построение плана, аргументы и обработку ошибок. Отдельный компонентный набор auth-service запускает собранную CLI на выделенном store OpenFGA. Он проверяет пагинацию, пакетные записи, отсутствие запросов записи при ошибке и повторном применении, полный граф и общий таймаут чтения выгрузки.

Ручные HTTP-проверки описаны в [Postman-инструкции](postman/README.md). Docker/submodule инфраструктура проекта утилитой не изменяется.

`space-types` — отдельная операторская CLI, а не команда пользовательского API. Она заполняет отсутствующие отметки UUID, типа пространства и владельца personal. Новые пространства получают эти отметки при синхронизации создания. По умолчанию команда лишь выводит план. `-request-timeout` задаёт бюджет полного чтения tuples и каждого write batch (default 5s), `-timeout` — общий бюджет запуска (default 10m). Оба параметра должны быть положительными. В сервисе используется `openfga.request_timeout`; defaults определены в слое config. При ошибке чтения частичный план не выдаётся. После обновления строгой модели нужно публиковать модель именно из новой сборки и указывать её ID. Этот бюджет распространяется также на проверку выгрузки, сортировку и сверку после записи. При отмене до записи утилита не выдаёт готовый план.

План в формате JSON выводится в `stdout`. Ошибки аргументов, чтения выгрузки, записи и итоговой проверки выводятся в `stderr`. При сбое записи сообщение указывает, сколько маркеров OpenFGA подтвердил и сколько было запланировано. Если ответ последнего пакета потерялся, его состояние уточнит повторный dry-run.

## Обновление с предыдущей строгой модели

Остановите создание пространств обоих типов и остальные writers, возьмите полную выгрузку и опубликуйте новую строгую модель. Если типы уже перенесены, выполните dry-run и apply на ID новой строгой модели, сохраняя строгие правила доступа. Для каждого существующего пространства план добавит недостающую связь `space:ID#created@user:*`. Для каждого прежнего personal план дополнит `user:OWNER#has_personal_space@user:OWNER`. Повторный dry-run должен вернуть пустой список записей. Убедитесь, что все writers перешли на новую версию, прежде чем открыть трафик. Два personal у одного владельца или лишняя отметка блокируют применение всего плана и требуют сверки с бизнес-данными.
