# Go Engineering Guide

## 1. Философия и архитектура

- Пиши идиоматичный, читаемый, поддерживаемый и проверяемый Go. Ориентируйся на Effective Go и Go Code Review Comments.
- Предпочитай явные зависимости, небольшие компоненты и композицию. Не считай количество строк мерой качества.
- Применяй KISS/DRY/YAGNI осмысленно: не дублируй ответственность, но не объединяй несвязанный код из-за внешнего сходства.
- Используй обычные функции для операций без собственного состояния; структуры с методами — для связанных данных, состояния и поведения.
- Рассматривай Strategy, Factory, Adapter и иные паттерны при конкретной необходимости (варианты поведения, сторонние API, сложное создание объектов). Не добавляй паттерны механически.
- Перед нетривиальным изменением изучи связанные реализации; сохрани публичные контракты, если их изменение не требуется.
- Организуй пакеты по ответственности. Избегай мусорных `utils`, `common`, `helpers`, циклических зависимостей, лишних слоёв и ненужного экспорта. Используй `internal`, если компонент не должен импортироваться извне.

## 2. Интерфейсы, nil, указатели и значения

- Делай интерфейсы небольшими; по возможности определяй их на стороне потребителя. Используй конкретный тип, если абстракция не нужна.
- Не используй `*interface` и `any` для обхода типизации. Не возвращай typed nil как ненулевой `error` или другой интерфейс; помни, что интерфейс с динамическим типом и nil-значением не равен `nil`.
- Проверяй `nil` только там, где он допустим контрактом, а не автоматически на каждом шаге. Не считай nil map пригодной для записи. Учитывай различие nil и пустых slice/map при JSON-сериализации.
- Используй pointer receiver для изменения состояния и для типов, которые нельзя безопасно копировать (например, содержащих `sync.Mutex`). Value receiver подходит небольшим значениям с корректной семантикой копирования.
- Не копируй mutex после первого использования. Помни, что копирование структуры со slice/map/pointer не выполняет глубокое копирование содержимого.
- Поддерживай разумно единый стиль receiver у методов одного типа. Не выбирай указатели исключительно по микрооптимизационным соображениям.
- Учитывай zero value и обратную совместимость при добавлении полей структур.

## 3. Generics

- Используй generics, если одна типобезопасная операция действительно общая для нескольких типов.
- Не заменяй обычные интерфейсы или конкретные функции generics ради новизны; предпочитай простые constraints и понятные сигнатуры.
- Не создавай универсальную абстракцию ради устранения нескольких строк дублирования.

## 4. Ошибки и освобождение ресурсов

- Проверяй существенные `error`. Оборачивай с полезным контекстом через `%w`, когда важно сохранить цепочку; для классификации используй `errors.Is`/`errors.As`, а не строки.
- Не используй `panic` для ожидаемых ошибок и не логируй один сбой на каждом слое. На границе внешнего API при необходимости преобразуй внутренние ошибки в безопасные публичные категории.
- Закрывай `http.Response.Body`, `sql.Rows` и другие ресурсы. Используй `defer`, когда это уместно, но не игнорируй ошибки `Flush`, `Close`, `Commit` и аналогичных завершающих операций, если от них зависит корректность результата.
- При частичном сбое освобождай ресурсы и сохраняй диагностически значимые ошибки. Не заявляй об успехе до завершения критичных финальных операций.
- Для повторов учитывай идемпотентность и неизвестный исход: сеть могла оборваться после успешного выполнения операции на стороне сервера.

## 5. Context, конкурентность и горутины

- Принимай `context.Context` первым параметром отменяемых операций и передавай его далее; не заменяй полученный context на `context.Background()`/`TODO()`.
- Задавай таймауты на внешних вызовах, где это необходимо. Вызывай `cancel()` дочерних контекстов. Не используй context для произвольной конфигурации и без необходимости не сохраняй его в структуре.
- Каждая горутина должна иметь осмысленный жизненный цикл и путь завершения при отмене, остановке или ошибке. Предусматривай ожидание завершения там, где оно нужно.
- Не допускай бесконтрольного создания горутин. Применяй ограничение конкурентности, worker pool, semaphore или `errgroup` по задаче.
- Защищай изменяемое состояние mutex/atomic или организуй владение им через каналы. Каналы не всегда лучше mutex. Избегай конкурентной записи в map без синхронизации и длительных I/O под mutex.
- Не используй `time.Sleep` вместо синхронизации. Race detector важен, но не обнаруживает все deadlock и логические гонки.
- Retry должен учитывать отмену context перед попыткой и во время ожидания. Не повторяй неидемпотентные операции без защиты от дублирования.

## 6. SQL и транзакции

- Используй параметризованные запросы, а не конкатенацию непроверенных значений в SQL. Синтаксис placeholders зависит от драйвера/БД.
- Для запросов используй `QueryContext`, `QueryRowContext`, `ExecContext` и аналоги. Обрабатывай `Scan`, `rows.Err()`, `rows.Close()` и ошибки операций.
- Для связанных атомарных шагов используй транзакции (`BeginTx`, операции через `*sql.Tx`, `Commit`); не выполняй часть транзакции через `*sql.DB` по ошибке. Отложенный `Rollback` допустим как страховка.
- Учитывай изоляцию, конфликты, повторное выполнение, блокировки и неоднозначный исход `Commit`. Не держи транзакцию открытой во время долгих внешних операций без оснований.
- Не предполагай поддержку SQL, транзакций, LWT или иных возможностей, которых нет у конкретного хранилища/драйвера. Для NoSQL определяй гарантии отдельно.
- Не включай секреты и чувствительные параметры запросов в логи.

## 7. Совместимость и границы системы

- Сохраняй экспортируемые сигнатуры и семантику возвращаемых значений, если изменение не согласовано.
- При изменении JSON/протоколов учитывай имена, типы полей, `omitempty`, zero values, совместимость старых клиентов и уже сохранённых данных.
- Не меняй бездумно sentinel errors и поведение ошибок, на которое опираются потребители.
- Для межсервисных изменений проверяй контракты обеих сторон; при несовместимых изменениях явно фиксируй план перехода.
- Не добавляй внешние зависимости без причины и не обновляй массово несвязанные зависимости.

## 8. Производительность и наблюдаемость

- Используй структурированные логи и диагностический контекст; не логируй токены, пароли и другие секреты.
- Не оптимизируй без измерения. Для значимых участков применяй benchmark, `b.ReportAllocs`, pprof и повторяемые сравнения.
- Исключай подготовку из измеряемой части бенчмарка, если она не предмет проверки; следи, чтобы оптимизатор не устранил тестируемую работу.
- Сохраняй читаемость и корректность при оптимизациях; мелкое ускорение не оправдывает трудно поддерживаемый код.

## 9. Документация

- Пиши содержательные комментарии на русском, если проект не требует другого языка. Комментарий экспортируемого объявления начинай с его имени согласно Go conventions.
- Документируй назначение и контракт, значимые побочные эффекты, ограничения и причины неочевидных решений.
- Не пересказывай код построчно и не заявляй гарантий, которых реализация не даёт. Особенно объясняй защиты от потери данных, удаления чужих ресурсов и повторов.

## 10. Работа ИИ и проверка изменений

- Перед задачей изучи текущий код, существующие интерфейсы, тесты и Makefile; не переписывай рабочие части без необходимости.
- После изменений добавь релевантные unit/регрессионные тесты и проверь сохранность контрактов.
- **Перед каждым коммитом обязателен успешный `make lint` и `make test`**. Используй существующие Make targets вместо дублирования инструментов вручную. Если менялся конкурентный код — запусти `go test -race ./...`, когда проверка не включена в Makefile.
- Не ослабляй проверки или assertions ради зелёного результата. Не выдавай непроведённые проверки за пройденные.
- Подробнее о тестах — `docs/testing-guidelines.md`, о шаблонах решений — `docs/architecture-examples.md`.
