# Go: правила тестирования и проверки надёжности

## 1. Обязательные договорённости

- Пиши тесты через стандартный `testing`, используй `testify/require` для утверждений.
- Во всех **независимых** тестах и подтестах вызывай `t.Parallel()`. Исключения (например, `t.Setenv`, `t.Chdir`, глобальные ресурсы) оставляй последовательными и объясняй.
- В проектах на **Go 1.24+** передавай `t.Context()` в тестируемые функции, принимающие `context.Context`. Для сценариев отмены/таймаута используй дочерние `context.WithCancel(t.Context())` / `WithTimeout` и вызывай `cancel`.
- `t.Context()` отменяется **до** `t.Cleanup`: если очистка требует активного контекста, создай для неё отдельный контекст с ограниченным временем. Учитывай, что `t.Setenv` и `t.Chdir` нельзя применять в параллельном тесте или его параллельном родителе.
- Используй `t.TempDir()` для файлов и `t.Cleanup()` для ресурсов. Не допускай обращения unit-тестов к production.
- Для нового теста выбирай один логически завершённый сценарий; несколько assertions одного сценария нормальны. Используй table-driven tests, если поведение одно, а входные данные варьируются.

## 2. Проверки через require

- `require.NoError(t, err)` — успех; `require.Error(t, err)` — наличие ошибки; `require.ErrorIs` — sentinel/обёрнутая ошибка; `require.ErrorAs` — тип ошибки.
- `require.ErrorContains(t, err, fragment)` — значимый фрагмент **сообщения** ошибки; не заменяй им `ErrorIs`/`ErrorAs`, когда важна классификация.
- `require.Equal(t, want, got)`, `NotEqual`, `Len`, `Contains`, `ElementsMatch`, `Nil`, `NotNil` — вместо самодельных `if got != want` и `require.True(t, got == want)`.
- Не сравнивай полный текст ошибки без причины; в общем случае используй `ErrorContains` для текста и `ErrorIs` для категории.
- Не проверяй одно свойство дважды без необходимости (например, `Error` перед `ErrorContains`).
- Не вызывай `require` и `t.FailNow`/`t.Fatal` из фоновых горутин: прекращение теста относится к текущей горутине и может привести к некорректному поведению.

## 3. Моки в table-driven тестах

- **Если тест использует моки, каждый кейс таблицы должен содержать `expect`, настраивающий ожидания конкретного сценария** (если структура кейса проекта уже использует близкое название/конвенцию — следуй ей).
- Пример: `expect func(*MockRepository)` либо `expect func(*Mocks)` при нескольких зависимостях.
- Настраивай ожидания внутри `expect`, а не в `if/else` по имени кейса, входным параметрам или ожидаемой ошибке.
- Создавай отдельные экземпляры моков **внутри каждого подтеста**, вызывай `expect` до тестируемого действия и проверяй, что ожидания выполнены (`AssertExpectations`, `Finish` и т. п. — по принятому фреймворку).
- Конкретизируй аргументы и количество вызовов, когда это контракт. Для запрещённых побочных эффектов проверяй отсутствие вызова (`AssertNotCalled` и аналог).
- Не используй моки там, где проще проверить реальный локальный компонент (например, файловую систему через `t.TempDir`). Не создавай фиктивное `expect` в тестах без моков.
- Не используй общие изменяемые моки между `t.Parallel`-подтестами.

## 4. Асинхронное поведение и время

- Для ожидания асинхронного состояния используй `require.Eventually(t, condition, waitFor, tick)` вместо фиксированного `time.Sleep`.
- Для нескольких условий с полезной диагностикой используй `require.EventuallyWithT` с проверками `assert.*` на переданном `*assert.CollectT`; не вызывай `require.*` внутри callback.
- Callback должен быть безопасен для повторных вызовов, потокобезопасен и не иметь разрушительных побочных эффектов.
- Когда можно использовать канал, явную синхронизацию или тестовые часы — предпочитай детерминированный подход. Не используй Eventually для синхронного результата.
- При необходимости подтвердить отсутствие события в интервале времени рассматривай `require.Never` и оцени устойчивость такой проверки.
- Для фоновых операций проверяй остановку по отмене контекста и отсутствие утечек. Убедись, что тест действительно достигает состояния, которое намерен проверять (например, worker уже запущен до отмены).

## 5. Надёжность и безопасность сценариев

- Проверяй наблюдаемое поведение, а не только внутренние вызовы.
- Для удаления/очистки проверяй **как удалённые, так и сохранённые** ресурсы; для ошибок валидации — отсутствие записи и внешних вызовов, если это контракт.
- Проверяй частичные отказы, таймауты, ошибки `Commit`, rollback, неуспешную очистку, ошибки внешних сервисов, отсутствие утечек секретов в ошибках/логах.
- Для retry проверяй виды повторяемых ошибок, максимум попыток, общий временной бюджет, отсутствие дублирования неидемпотентных операций, отмену контекста.
- Используй синтетические токены и изолированные сервисы. Unit-тесты не должны случайно запускать реальный Docker, Telegram API, продовую БД или облачное хранилище.
- При изменении межсервисных форматов добавляй тесты совместимости старых и новых значений, если это важно.
- При исправлении бага добавляй регрессионный тест, который бы падал при возвращении дефекта.
- Используй `go test -race ./...` для конкурентного кода; отсутствие найденных гонок не доказывает отсутствие всех проблем.

## 6. Дополнительные режимы тестирования

- Тесты не должны зависеть от порядка выполнения. При изменении тестовой инфраструктуры или нестабильных падениях используй `go test -shuffle=on -count=10 ./...`, если это безопасно.
- Fuzz-тесты подходят парсерам, сериализаторам и недоверенному вводу, когда можно проверить инварианты; не создавай их для каждой функции.
- Для реального SQL нужны отдельные интеграционные тесты с изолированной БД; unit-моки не подтверждают правильность SQL-семантики. Интеграционные тесты должны быть явно отделены от безопасного unit-набора.

## 7. Перед каждым коммитом

1. Посмотри, что именно запускают `lint` и `test` в **существующем Makefile**.
2. Выполни `make lint` и `make test`: **обе команды должны пройти** перед каждым коммитом.
3. Если изменён конкурентный код, дополнительно выполни `go test -race ./...`, если это не входит в Make targets.
4. Исправь ошибки, повтори необходимые проверки. Не меняй тесты/линтеры ради скрытия дефектов.
5. Не сообщай об успехе непроведённых проверок. Если невозможно запустить — объясни блокировку и не коммить заведомо падающие изменения.

> Этот документ задаёт правила, а не изменяет Makefile или CI автоматически. Уточняй состав проверки по реальному репозиторию.
