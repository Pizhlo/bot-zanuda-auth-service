# Инструкции для ИИ: Go

Перед изменением Go-кода прочитай:
- `docs/codestyle/go-engineering-guide.md` — архитектура, идиомы Go, ошибки, БД, конкурентность и надёжность.
- `docs/codestyle/testing-guidelines.md` — правила тестов и обязательные проверки.
- `docs/codestyle/go-architecture-examples.md` — примеры выбора решений. Примеры условные; не копируй их без адаптации к API проекта.

## Приоритеты

1. Сохраняй существующие контракты и стиль проекта; изучи близлежащий код и Makefile.
2. Предпочитай простой, идиоматичный и тестируемый Go; интерфейсы и паттерны — только по делу.
3. Правильно обрабатывай `error`, `context.Context`, конкурентный доступ и освобождение ресурсов.
4. Не допускай утечек горутин, секретов и нежелательных побочных эффектов.
5. Для публичного API и межсервисных форматов учитывай обратную совместимость.

## Git: ветки и коммиты

1. **До начала изменения кода** проверь текущую ветку (`git branch --show-current`) и состояние репозитория (`git status`). Убедись, что рабочая ветка соответствует текущей задаче.
2. Работай над задачей **только в её feature-ветке**. Стандартное имя ветки — идентификатор задачи `BZ-N` (например, `BZ-123`); если в репозитории есть более точное соглашение с суффиксами, следуй ему.
3. **Перед началом работы обязательно уточни у пользователя, правильная ли это ветка**, назвав текущую ветку и номер задачи. Не предполагай, что уже открытая feature-ветка относится к новой задаче: она могла остаться от предыдущей работы. Если подходящая ветка не подтверждена, не меняй код и не создавай коммит.
4. Для новой задачи создавай feature-ветку **от актуального `main`**, предварительно безопасно обновив сведения об удалённом репозитории. Не используй старую feature-ветку как базу. Перед переключением или обновлением проверь незакоммиченные изменения; не сбрасывай и не перезаписывай чужую работу.
5. **Каждый коммит должен начинаться с идентификатора задачи**: `BZ-123: ...`. Описание после двоеточия пиши **на русском, в прошедшем времени**, о том, что сделано: `BZ-123: добавлены проверки восстановления бэкапов`, `BZ-123: исправлена обработка таймаута`.
6. Не используй сообщения в повелительном или будущем времени: `BZ-123: добавить тесты`, `BZ-123: будет исправлено`. Указывай фактически выполненное изменение, без общих формулировок вроде `fix` или `update`.
7. Перед **каждым** коммитом успешно выполни `make lint` и `make test`; не создавай коммит с известными ошибками проверок.
8. Не выполняй `git commit`, `git rebase`, `git reset --hard`, `git push --force` и другие потенциально меняющие историю действия без соответствующего разрешения и проверки последствий.

## Тесты

- Для безопасно независимых тестов и подтестов используй `t.Parallel()`; не допускай общего изменяемого состояния.
- При Go 1.24+ для тестируемых операций используй `t.Context()`, кроме случаев, когда тест специально проверяет другой контекст.
- Проверяй результат через `github.com/stretchr/testify/require` (`Equal`, `NoError`, `ErrorIs`, `ErrorAs`, `ErrorContains`, `Len` и др.), а не ручными `if` для обычных сравнений.
- Для ожидания асинхронных условий используй `require.Eventually` / `require.EventuallyWithT`, если не подходит детерминированная синхронизация. Не применяй фиксированный `time.Sleep` для ожидания результата.
- В table-driven тестах с моками настройку ожиданий помещай в поле `expect` каждого кейса. Создавай отдельные моки для каждого подтеста и проверяй ожидания; следуй существующему mock-фреймворку.
- Не вызывай `require` / `t.Fatal` из фоновых горутин.
- Проверяй ошибки, отмену, частичные отказы, отсутствие запрещённых побочных эффектов; добавляй регрессионные тесты при исправлении дефектов.

## Перед каждым коммитом

1. Изучи цели `lint` и `test` в существующем Makefile.
2. **Обязательно запусти `make lint` и `make test`; обе команды должны завершиться успешно.**
3. При изменении конкурентного кода дополнительно запусти `go test -race ./...`, если это ещё не делает Makefile.
4. При поиске нестабильности или изменении тестовой инфраструктуры используй `go test -shuffle=on -count=10 ./...`, когда это безопасно и применимо.
5. Исправь ошибки и повторно запусти проверки. Не ослабляй тесты, линтеры и правила только ради зелёного результата.
6. Если проверить код нельзя, явно сообщи причину и не утверждай, что проверки пройдены. Не создавай коммит с заведомо падающими обязательными проверками.

## Безопасность изменений

Не запускай тесты или команды, обращающиеся к production либо выполняющие разрушительные действия, без явного разрешения. Вноси минимально необходимые изменения и не проводи посторонний рефакторинг.
